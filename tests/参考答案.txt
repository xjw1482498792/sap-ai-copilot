1）项目整体架构、你的分工，哪些代码是你独立开发？
架构层级：
	主要分为四大层级：
	1是应用交互层，负责接收用户自然语言问题,将请求传入agent，返回最终生成的业务数据
	2是agent流程层，基于langgraph定义三个核心节点，和节点之间的条件边
	3是agent能力层，封装api调用、及调用所需的tool定义、prompts组装、rag检索、历史会话维护等方法
	4是db持久层，封装SQLite数据库查询方法，供agent层调用并检查执行结果

我的职责及最核心的内容：
	langgraph的节点流程设计及api调用核心代码都是我独立完成，包括api调用所需的rag召回数据，tool封装，prompt组装，历史会话维护等


执行流程：
	当用户输入自然语言后，首先本地的BGE模型会将自然语言转换为512维度向量，然后chroma向量库根据向量余弦相似度，检索出前5条完整SAP业务表结构。接着进入langgraph流程中，共有三个节点：generate节点负责生成SQL；execute节点负责执行SQL；reflect节点负责反馈错误。
	进入generate节点后，将RAG检索召回的5个完整的表结构和数据库全部表的简略结构放入system提示词，完整结构用于生成sql，简略结构用于召回不足时调用tool。将用户问题放入user提示词，按照规范将tool定义的方法名和参数一并传入API调用接口，由模型给出回答。模型回答通常有两种：1是直接生成SQL，进入execute节点  2是RAG召回的表数量不全，需要调用tool查询其他表的结构。   根据模型返回的表名，由程序调用方法查询出完整表结构。   将模型调用tool的请求和方法返回的结果维护至历史会话中，开始下一轮API调用，直至表结构足以生成SQL或者调用次数达到上限。然后对模型返回SQL进行标准化，去除多余解释性语言进入execute节点
	进入execute节点后，调用SQLite接口，真正地执行SQL。将执行SQL和结果计入State状态对象中。执行成功的标准是是否抛出异常， 执行成功，流程结束，执行失败且在自修复次数内会进入reflect反馈节点。
	在reflect节点中，从state状态对象取出历史执行记录，分析最近的重复性错误。如果最近发生了2次或以上同类型的错误，记录重复的错误和发生的次数。 当下一轮进入generate节点后，会把历史执行记录和最近错误一并放入user提示词，开始下一轮的生成。
	最终生成可执行的，贴合真实表结构的SQL


技术栈：
	主要以python语言开发为主，langgrapth框架维护流程和状态，BGE模型做中文向量化，Chroma向量库做向量检索，Deepseek API分析和生成SQL，SQLite数据库存储真实的业务数据。

2）项目最大难点，Python层面如何解决？（性能、并发、内存、数据库慢查询）
bug与难点：
	项目最大的难点不是传统的python技术问题，而是如何处理大模型输出的不确定性。
	虽然我在system prompt中明确要求模型只返回纯净的可运行SQL，并把temperature设置为0，但模型仍然可能返回Markdown围栏、中文开场白，和后续解释话语等。
	对于模型输出的概率性问题，我在python中做了多层兜底机制。
	首先通过自定义方法对模型输出结果进行标准化：使用正则表达式去掉Markdown围栏，定位第一个SELECT、WITH等关键字，截掉SQL后面的解释性内容。	
	清理完成后，系统会把SQL交给SQLite实际执行。如果还有问题如，字段不存在、语法错误等其他错误，会把执行结果计入langgraph状态中，经过reflect反馈节点后重新生成。
	这样就形成了“提示词约束-python清洗-数据库验证-agent自修复”多层容错机制
	
	bug单独摘出来：
	这里曾遇到一个bug，最初的规则是把所有以中文开头的行都算中文解释，但SQL中可能存在中文字段别名，导致合法SQL被误截。
	后来我把规则改为白名单匹配，只有中文行中包含“所以”，“根据”等明显话术时，才认为是解释性内容。

1）深浅拷贝区别、应用场景
	通常赋值、浅拷贝、深拷贝会放在一起比较。
	赋值是给引用对象新增了一个入口，没有copy任何对象。
	浅拷贝是copy外层对象，复用内层对象。如一个二维列表，copy后外层地址是新的，每一行的列表仍然复用原来的列表。
	深拷贝一般递归copy所有层级对象，内层和外层都是新的地址。
	应用场景主要依据拷贝的程度选择

2）多线程/多进程/协程适用场景，GIL锁限制	
	gil全称python全局解释器锁，本质是一把互斥锁，
一个进程多个线程执行python字节码前，需要先获取锁。
这就使得同一时刻只有一个线程能执行python字节码。 
	在python中，io密集型任务通常选择多线程和协程处理，
由操作系统调度线程或事件循环调度协程，提高io等待效率；
由于gil的存在，cpu密集型任务通常选择多进程处理，
真正并行执行任务，而不能选择多线程。

3）装饰器、生成器原理，手写简易计时装饰器
	装饰器本质是一个加工函数的函数。
	内层定义wrapper函数接收原函数参数，执行并返回原函数返回值，在不改变原函数的前提下，追加其他逻辑，如日志，计时等功能。
	使用方法在原方法上@装饰器名

	通过在函数内使用yield关键字，定义生成器函数。生成器函数返回生成器。
	第一次通过next执行生成器，遇到yield时，会暂停执行；
	下一次调用next执行时，会从暂停位置继续执行
	#计时装饰器	
	import time
	from functools import wraps

	def timer(func):
		@wraps(func)
		def wrapper(*args, **kwargs):
			start = time.perf_counter()

			try:
				return func(*args, **kwargs)
			finally:
				elapsed = time.perf_counter() - start
				print(f"{func.__name__} 耗时：{elapsed:.4f} 秒")

		return wrapper

	@timer
	def query_data(delay):
		time.sleep(delay)
		return "执行成功"

	if __name__ == "__main__":
		result = query_data(2)
		print(result)

4）with上下文管理器原理，文件/数据库连接好处
	with上下文管理器用于管理资源的获取和释放，一个对象要支持with语句，需要实现enter和exit方法。
	进入with代码块时，会调用enter方法获取资源，他的返回值会赋给as后面的变量；退出代码块时，无论正常结束还是发生异常，都会调用exit方法释放资源。
	最大的好处就是不用手动维护释放资源的逻辑

5）MySQL慢查询优化、Redis缓存击穿/雪崩解决方案	
	先通过慢查询日志定位耗时较长的SQL，
	然后使用explain analyze分析扫描行数和索引使用情况等信息。
	可以通过创建符合查询条件的联合索引调高查询效率

	redis缓存击穿：
	热点key的缓存在某个时刻突然失效，大量请求访问数据库。
	通过在访问数据库前加锁，使得第一个请求取出数据后，写入缓存。
	然后后续其他请求访问缓存(防止竞争锁的其他请求仍然访问数据库，在获取锁后须再执行一次查缓存)
	redis缓存穿透：
	当某个查询请求既未命中缓存，在不存在与数据库中。写入空缓存值
	redis缓存雪崩：
	大量缓存同时失效，通过设置随机过期时间预防。
